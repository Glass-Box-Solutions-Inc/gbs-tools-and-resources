WC Synthetic Caseload Engine

A user guide for generating complete, byte-reproducible synthetic California workers’ compensation attorney case files — for Adjudica demo accounts, classifier training corpora, and testing.

Package packages/wc-synthetic-caseload-engine Version 0.1.0 Tickets AJC-34, AJC-36 CLI wc-caseload
Section 1

What it is, and why

The engine turns a small YAML seed into a complete synthetic California workers’ compensation attorney case file — the kind that reads as if an applicant-side firm actually produced it, right down to lien conferences that end in executed lien resolution agreements and petitions for reconsideration that come back remanded and settled on remand.

Write one CaseSeed per case — who was hurt, how, how far the case went, which legal doctrines flavor it, and exactly which documents you want in what quantities and formats — run one command, and get back a folder of rendered documents plus a manifest describing every one of them. The same seed regenerates the same caseload forever, byte for byte.

The problem it solves

Adjudica demo accounts held five document-free matters and one hand-populated case. The closest existing tool, merus-test-data-generator, generates documents at scale but takes only CLI flags: no per-case seed artifact to review, no reconsideration round-trips, thin lien modelling, and no fine-grained per-case document controls. Because nothing could generate targeted documents to specification, the classifier’s accuracy corpus covered only 97 of its 353 subtypes.

This engine adds control on top of that substrate. It consumes merus-test-data-generator as a library — the 25 ReportLab template classes, the content pools, the lifecycle machinery — and never copies or edits it. This package owns the seed schema, the lien and reconsideration machines, document-control precedence, determinism fixes, and manifests; the substrate owns rendering.

What you get out of one run

  • A reviewable seed.yaml per case — even auto-derived cases are always materialized to disk, so nothing about a case is implicit.
  • Rendered documents in up to four formats: pdf, scanned_pdf, eml, docx.
  • A per-case manifest.json and a caseload-level caseload_manifest.json, both carrying provenance so every byte can be traced back to the seed and the substrate commit that produced it.
  • A guarantee that the same seed and engine version reproduce the identical bytes — on any machine, in any timezone, on any day.

Generation never touches the network and never writes outside the directory you pass to --out.

Section 2

Install & quickstart

The substrate package, packages/merus-test-data-generator, must be checked out alongside this one (both live under packages/ in the gbs-tools-and-resources monorepo, so this is automatic in a normal checkout). If it lives somewhere else, point at it with the WC_CASELOAD_SUBSTRATE=/abs/path environment variable.

Install

uv venv --python 3.12
uv pip install -e ".[dev]"

Run from inside packages/wc-synthetic-caseload-engine/. This creates .venv/ and installs the wc-caseload console script into it.

Generate the demo caseload in three commands

wc-caseload generate --spec examples/demo-caseload.yaml --out /tmp/wcce-demo
wc-caseload validate --out /tmp/wcce-demo
wc-caseload taxonomy-check

The first command resolves the demo caseload, plans every case, renders every document and writes manifests. On a real run this produces 7 cases and 331 documents across all four formats. The second confirms every manifest subtype is canonical and every checksum matches what is on disk. The third confirms the engine’s taxonomy hasn’t drifted from the classifier it feeds.

The demo also prints two doctrine warnings, on purpose — it carries two hooks whose cases cannot support them, to exercise the kept-and-warned path described in Section 8. For the opposite exercise, a warning-free run covering all fourteen doctrines, generate examples/doctrine-showcase.yaml instead (Section 9).

Tip Add --dry-run to generate to validate and print the resolved plan (one line per case: seed, stage, injury, claim response, resolution, lien count, whether recon fired) without writing anything. Useful for sanity-checking a spec before committing to a render, which is the slower step.

Section 3

The CaseSeed YAML

One case is one CaseSeed. Every field except case_id, rng_seed and injury has a default, and anything you omit is derived deterministically from rng_seed. This is the whole point: the seed is the interface, and it is designed so that a one-line seed (case_id + rng_seed + injury) is already valid and produces a fully realized case.

Get the canonical, fully-annotated template any time with:

wc-caseload seed --template --out seed.yaml
Strict by design Unknown fields and invalid enum values are rejected at load time, naming the dotted field path, the allowed values, and the offending input. A typo never silently generates the wrong caseload — see Runway validation below for exact error text.

Full annotated example, field by field

This is the live output of wc-caseload seed --template --kind case, reproduced in full:

Runway validation: what gets rejected, and how to read the error

A seed states how far its case got; the calendar decides whether that is possible. This engine anchors "today" at a fixed date, 2026-01-01 (never the wall clock — see Determinism), and every lifecycle stage needs a minimum number of days between the injury and that anchor to hold its own story: an Application follows the injury by two to six months, resolution by another six, a petition for reconsideration within 25 days of the award, and the WCAB’s order within 60 more.

A seed whose injury sits too close to the anchor for the story it claims is rejected at load time, before any rendering happens. Verified live against the CLI, an over-tight seed produces:

Error: bad-runway.yaml: 1 validation error(s)
  cases.0: Value error, injury.date_of_injury is 2025-06-01, which leaves
  214 day(s) before the 2026-01-01 anchor, but lifecycle.target_stage
  'resolved' needs at least 540. Move injury.date_of_injury to 2024-07-10
  or earlier, or seed a lifecycle that reaches less far.

The message names the offending field, the actual runway available, the driver that demanded more, the minimum it needed, and a concrete fix — either move the date or seed a lifecycle that reaches less far. Exit code is nonzero (1).

Runway floors

DriverMinimum runway
target_stage: intake30 days
target_stage: active_treatment / discovery180 days
target_stage: medical_legal / pre_trial365 days
target_stage: resolved, or any resolution.type other than pending540 days
target_stage: post_recon, reconsideration.enabled, or liens.post_resolution_litigation720 days

This replaced an earlier behavior of silent clamping, which absorbed a short runway by pinning over-horizon dates onto the anchor — producing, in one real case, a petition for reconsideration dated 80 days before the Application it appealed from. Sequenced chains (each lien track, the reconsideration round trip) are fitted as a whole rather than clamped date by date, so a tight window compresses them in order with strictly increasing dates instead of stacking several documents on one day. A lien track seeded with post_resolution_litigation: true is allowed to run past the anchor rather than be compressed, because post-resolution lien practice genuinely outlives the case-in-chief. Auto-derived seeds (see next section) satisfy these floors by construction, so you will only meet this error when hand-writing a seed.

Section 4

Case perspective: applicant or defense

One injury, two case files. The applicant firm’s folder and the defense firm’s folder describe the same claim and share most of their paper, but the privileged half of each is written by a different lawyer for a different client. The top-level perspective field on CaseSeed picks which folder you are generating:

case_id: whitaker-defense-qme-surveillance
rng_seed: 100007
perspective: defense   # applicant (the default) | defense

It sits right after rng_seed and before profile in the schema, and defaults to applicant when omitted — every seed written before this field existed still resolves to applicant and plans, dates and renders exactly as it always did.

Not yet in seed --template Verified live: as of this writing, wc-caseload seed --template --kind case does not print a perspective: line in its annotated output — the field is real and live in the schema (it is on CaseSeed, it drives --dry-run’s pov= column, and it is recorded in every manifest) but the generated template text itself has not been updated to demonstrate it yet. Until it is, add it by hand as shown above, or copy it from the demo caseload’s whitaker-defense-qme-surveillance case in examples/demo-caseload.yaml.

The invariant: perspective never changes a case fact

Same rng_seed, same everything else: identical cast — both firms exist in both files, because they are opposing counsel, not alternatives — identical ADJ number, identical date of injury, identical lifecycle event dates. Only the file’s point of view moves.

That is enforced structurally rather than by convention. perspective is never mixed into an RNG salt that feeds a fact — the module draws only from its own salt, "perspective", a stream nothing fact-producing reads, used solely to date the paper this side of the file adds on its own. On the applicant path, apply_perspective() is a literal identity function that draws no randomness at all, which is exactly what keeps every seed written before this field existed byte-stable.

Three things change, all in perspective.py

1. Work-product swap

Privileged analysis belongs to whoever owns the file, so a defense file calls it something else:

Applicant fileDefense file
CASE_ANALYSIS_MEMODEFENSE_CASE_ANALYSIS
SETTLEMENT_VALUATION_MEMODEFENSE_MSC_STATEMENT
TRIAL_BRIEFDEFENSE_TRIAL_BRIEF

All six are canonical WORK_PRODUCT subtype keys, so the swap is a rename and never a taxonomy escape. SETTLEMENT_VALUATION_MEMO maps to DEFENSE_MSC_STATEMENT because that is where a defense file states its valuation: the mandatory settlement conference statement is the defense’s number, filed rather than filed away. Work product both sides prepare under the same name — MEDICAL_CHRONOLOGY_TIMELINE, DEPOSITION_SUMMARY — deliberately does not swap.

2. Emission profiles

A table of per-subtype-or-parent-type weights multiplies what the shared lifecycle proposed. A subtype row beats its type’s row; a key with no row is carried unchanged by both files.

KeyApplicantDefenseWhy
CLIENT_CORRESPONDENCE_INFORMATIONAL / _REQUEST1.01.0Both firms write to their own client; only the roles invert.
CLIENT_INTAKE_CORRESPONDENCE1.00.0Defense counsel is assigned by a carrier; it runs no intake.
CLIENT_STATUS_LETTERS1.00.0Status letters go to an injured worker.
ADVOCACY_LETTERS_* (PTP/QME/AME)1.00.0Lobbying a physician toward a finding is applicant-side practice.
SETTLEMENT_DEMAND_LETTER1.01.0Applicant-authored; the defense file holds it as received mail.
CLAIMS_ADMINISTRATION (type)1.02.5The carrier’s own claim file — reserves, diary notes, nurse case management.
INVESTIGATION (type)1.03.0 + floorSub-rosa surveillance and social-media workups are defense-retained.

A positive weight never rounds a non-empty pool down to nothing; only an explicit 0.0 removes a document type entirely. INVESTIGATION is the one case a multiplier alone cannot express: the shared lifecycle proposes zero investigator reports, and any multiple of zero is zero. So its row also names a floor — subtypes planted once each when the characteristic side’s pool is otherwise empty. Defense files get INVESTIGATOR_REPORT, SURVEILLANCE_VIDEO and SOCIAL_MEDIA_EVIDENCE planted this way. “Characteristic side” is whichever weight is strictly higher; equal weights plant nothing.

Why the floor outranks routine paper Floor-planted documents are placed at a deliberately high priority (15, near the top of the core track) so documents.global_cap cannot delete them. Early testing found the demo’s defense file emitting zero investigation documents under global_cap: 55: the cap consumed the entire floor before it reached the twenty-third adjuster letter, so the one mechanism whose whole job is “this file always has surveillance” reliably produced a file with none. A floor the weakest control can delete is not a floor.

Perspective is a default, not a veto. An explicit documents.overrides entry still forces applicant-only paper into a defense file, through the same forced-emission path as any other lifecycle-invalid override (see Document controls), with a WARN that names the perspective as what it is overruling.

3. Roles

“Client” means the injured worker on an applicant file and the employer/carrier on a defense file, so the author and recipient of client correspondence invert. Documents the file owner authors — work product, client correspondence — get the owner’s attorney as author and the owner’s client as recipient. Everything else keeps the author the facts give it: an Application for Adjudication is applicant-filed in both files, an order is the judge’s in both. That document is instead addressed to the firm that owns the file, which is what makes it received paper.

Known limitation: defense docx letterhead

The substrate hard-codes Martinez & Associates, APC on the .docx letterhead (data/docx_styles.py), so .docx files in a defense case file carry the applicant firm’s letterhead. This is the same limitation already documented for profile.attorneys.applicant_firm (see Known limitations), now with a second visible symptom, and it is left unpatched for the same reason: rewriting a substrate module’s private constant at runtime would be shared mutable state across cases, and this package consumes the substrate as a library rather than editing it.

The defect is scoped to the rendered docx letterhead only. The manifest, the seed, the subtype set, the roles and every other format are unaffected — live-verified against the demo caseload’s defense case, whitaker-defense-qme-surveillance, whose manifest.json correctly records "perspective": "defense" alongside the correct applicantFirm and defenseFirm values regardless of the docx letterhead limitation.

Live example from the demo caseload

examples/demo-caseload.yaml now includes a seventh case, whitaker-defense-qme-surveillance: an accepted claim with a disputed QME apportionment, sub-rosa surveillance, and a C&R — generated with perspective: defense. Regenerating it live confirms the mechanics above: its 55-document file contains DEFENSE_MSC_STATEMENT, SURVEILLANCE_VIDEO, SOCIAL_MEDIA_EVIDENCE, INVESTIGATOR_REPORT, RESERVE_WORKSHEET, COMPENSABILITY_DETERMINATION and DEFENSE_COUNSEL_LETTER_INFORMATIONAL — and contains no CLIENT_INTAKE_CORRESPONDENCE or any ADVOCACY_LETTERS_* subtype at all, exactly as the emission-profile table predicts. Section 5

CaseloadSpec: defaults, explicit cases, and auto derivation

A caseload spec is what you pass to --spec. It combines a shared defaults block, an explicit list of hand-written cases, and an optional auto: block that derives additional fully-materialized cases from a calibrated distribution.

caseload_id: demo-2026q3

defaults: {<partial CaseSeed>}   # deep-merged UNDER each case

cases: [<CaseSeed>, ...]

auto: {count: 20, distribution: balanced, rng_seed: 777}

How defaults merges

defaults is a partial CaseSeed deep-merged under each entry in cases[] — mappings merge key-by-key, and any field the explicit case sets wins. Lists are replaced wholesale by the case, not concatenated. defaults does not apply to auto-derived cases; those are already fully materialized by the distribution.

From the demo caseload spec, the shared defaults set format mix and output settings once instead of repeating them per case:

defaults:
  documents:
    format_mix: {pdf: 0.6, scanned_pdf: 0.25, eml: 0.1, docx: 0.05}
  output:
    filename_style: neutral
    formats: [pdf, scanned_pdf, eml, docx]

A second example, from the caseload template, shows a case overriding one defaulted field (claim_response) while inheriting the rest:

defaults:
  lifecycle:
    claim_response: accepted
    eval_type: qme
cases:
  - case_id: martinez-001
    ### ...
    lifecycle:
      claim_response: denied          # overrides the default above

Auto derivation and the four distributions

auto: {count, distribution, rng_seed} derives count additional cases from a named distribution, fully seeded from rng_seed. Auto-derived seeds are always materialized to <out>/<case_id>/seed.yaml — the seed is the surfaced contract, never an implicit one, even for cases you never hand-wrote.

DistributionShape
balancedMirrors the KB PRD attorney-caseload mix — all stages represented.
early_stageIntake through discovery; nothing resolved.
settlement_heavySettlement and resolved files; liens common.
complex_litigationTrials, liens, reconsideration round trips.

Use --seed N on generate to override auto.rng_seed for a single run without editing the spec file — explicit case seeds in cases[] are untouched by this flag.

Section 6

Fine-grained document controls

Every case’s lifecycle proposes a set of documents on its own. The documents block lets you reshape that set precisely — force a subtype in, keep one out, bound a category, or cap the total. The controls compose through a strict precedence order, highest wins:

1Per-subtype override — {subtype: X, count: N} emits exactly N, even if the lifecycle never proposed that subtype and even if a blacklist or the cap would otherwise remove it. Forcing a lifecycle-invalid subtype works and logs a WARN: explicit control wins, loudly.
2include_only / exclude — whitelist then blacklist, each matching either a subtype key or a parent type key.
3Per-type min/max — bounds the surviving total for a parent type.
4Lifecycle emission defaults — what the core/lien/recon machines proposed on their own.
5global_cap — trims last, taking the most-trimmable documents first: filler, then supporting, then core; within a track, the highest priority number goes first. Never trims a per-subtype override and never pushes a type below its min.

Counts are resolved first, without dates; dates are then re-attached from the proposing candidate, and any copies beyond what the lifecycle originally proposed continue the same date series deterministically — so asking for extra copies of a subtype never produces documents dated out of order.

Worked example

documents:
  global_cap: 120
  format_mix: {pdf: 0.6, scanned_pdf: 0.25, eml: 0.1, docx: 0.05}
  include_only: []
  exclude: []
  overrides:
    - {subtype: DEPOSITION_TRANSCRIPT, count: 2}
    - {type: MEDICAL_CLINICAL, min: 8, max: 25}

Here, exactly two DEPOSITION_TRANSCRIPT documents always land in the plan regardless of what else happens; the MEDICAL_CLINICAL parent type is held between 8 and 25 documents after any whitelist/blacklist is applied; and if the case still exceeds 120 documents after all that, the global cap trims the least-essential remainder without violating either rule above it.

Control keys are canonicalized before anything reads them

A control key may be a canonical subtype, one of the 15 parent type keys, or a substrate-only key with an unambiguous canonical equivalent — which is translated through the same table the lifecycle walk normalizes through, so a control and a candidate always mean the same thing by the same rule. Anything else is refused rather than guessed at, and the error lists every offending key at once so fixing a spec is not an exercise in repetition:

k1: documents.exclude = 'NOT_A_REAL_SUBTYPE' is neither a document type
    nor a known subtype
Error: 1 document control key(s) are not valid taxonomy keys

Live-verified from wc-caseload validate --spec. The same check runs inside generate, so an unusable key can never reach a manifest.

Aliases collide after canonicalization, not before Three substrate keys canonicalize to CLIENT_CORRESPONDENCE_INFORMATIONAL, and two more such pairs exist. So include_only: [CLIENT_CORRESPONDENCE_INFORMATIONAL] together with exclude: [CLIENT_REPORT_ANALYSIS_LETTER] is one subtype written two ways — the schema validator compares raw strings, sees no overlap, and the resolver would then quietly drop the include you explicitly asked for. Every check the schema runs on raw keys is therefore re-run on canonical ones, and the error names the aliases you actually wrote (live-verified): documents.include_only and documents.exclude name the same subtype under different substrate aliases — CLIENT_CORRESPONDENCE_INFORMATIONAL (include_only: 'CLIENT_CORRESPONDENCE_INFORMATIONAL', exclude: 'CLIENT_REPORT_ANALYSIS_LETTER'). Name it once, canonically. The same re-check catches a list that names one subtype twice under two aliases.

Section 8

Doctrine hooks: what they inject, and what gates them

lifecycle.doctrine_hooks names the landmark California authorities a case is really about. Naming one does three things: it is recorded in the manifest, it steers which subtypes the lifecycle proposes, and — the part this section is about — it injects doctrine-specific language into the documents where a real practitioner would actually argue it.

The two registers

A doctrine reads differently depending on who is writing. A QME does not brief a case and an attorney does not offer a clinical opinion, so each hook carries two independent bodies of prose and the engine picks by the document’s own subtype:

RegisterAppended headingLands on
Medical-legalADDENDUM — MEDICAL-LEGAL DISCUSSION OF CONTROLLING AUTHORITYQME/AME reports, apportionment and impairment reports, psych evaluations, vocational and earnings-capacity opinions.
LegalPOINTS AND AUTHORITIES — CONTROLLING DOCTRINETrial briefs, petitions for reconsideration, answers, denial letters, rating and apportionment worksheets, settlement valuation memos, compensability determinations.

Each register is three paragraphs plus the full citation, appended as a titled section at the end of the document’s own story. A document carrying several hooks gets several sections, always in the order the hooks appear in DOCTRINE_CONTENT rather than the order you happened to write them in the seed — so two seeds naming the same hooks in different orders produce identical bytes.

Which documents get flagged

Every hook names its own target subtypes per register, and a document is flagged only when its subtype is in the set. That is deliberately narrow: a doctrine appended to every document in the case would be noise, not realism. The engine records the decision at plan time on PlannedDocument.content_flags, and the manifest carries it through as contentFlags — present only on documents that actually received language, never as an empty array:

{
  "filename": "028_2022-12-04.pdf",
  "subtype": "QME_REPORT_INITIAL",
  "type": "MEDICAL_LEGAL",
  // ... format, dates, checksum ...
  "template": "QmeAmeReport/qme_initial",
  "fallback": false,
  "contentFlags": ["almaraz_guzman"]
}

Live-verified from the demo caseload’s alvarez-denied-recon-remand, where 7 of 55 documents carry a contentFlags entry.

Provenance, not decoration contentFlags records what was applied to that file, not what the seed asked for. It is written from the renderer’s own return value after canonicalization, so a hook the seed named but the document’s subtype does not target never appears — which is what makes the field usable as ground truth for a classifier or an audit.

Prerequisite gating: a doctrine needs facts to argue from

A death-benefits argument in a living applicant’s file is not a feature. Every hook therefore carries a prerequisite — a predicate over the seed’s own fields — and the engine treats a failed prerequisite differently depending on who asked for the hook:

1You named it → kept, and warned about. An explicit doctrine_hooks entry is a choice, and the same rule that governs document controls governs this: explicit control wins, loudly. The hook stays, the language renders, and the case records a warning.
2The distribution drew it → filtered out silently. An auto-derived case (auto:) draws hooks from a pool that has already been filtered against the same prerequisites. A draw is nobody’s choice, so there is nothing to respect and nothing to warn about.

The warning is verbatim from a live run of the demo caseload, whose nguyen-cr-three-liens case names benson on a single-body-part claim precisely to exercise this path:

lifecycle.doctrine_hooks names benson on a case that cannot support it:
apportioning between injuries needs a rating and more than one impaired
region to argue about — lifecycle.eval_type must not be none and
injury.body_parts must name at least two parts. The hook is kept and its
language will be rendered (an explicit seed wins), but the argument will
not match the rest of the file.

It is emitted twice: as a WARN on the console (doctrine.unsupported_hook) and as an entry in the case manifest’s warnings array, so a caseload generated in CI can be checked without scraping logs. generate prints a run-level tally — warnings : 2 (see per-case manifest 'warnings') — and still exits zero, because a deliberately-unsupported hook is a legitimate thing to seed.

A prerequisite approximates a doctrine; it does not prove one

A gate is exact when a seed satisfying it must also satisfy the doctrine’s own factual predicate, and an approximation when the seed can pass the gate while the predicate stays unknown. Approximations exist because a CaseSeed models one injury, no prior award, no prior disability, no diagnosis, no employment-event history, and no grounds of denial — so some doctrines can only be gated on the closest thing a seed can establish.

Which hooks fall on which side is settled in one authoritative table in the README (“Which gates are exact, and which approximate”), with the full predicate and gate for all fourteen. This guide deliberately keeps no list or count of its own: two enumerations drift, and this one has drifted before.

The paragraphs an approximating hook injects are written as a contention register — what each side asserts and what the trier must decide — rather than as findings: “Where a prior award is established…”, not “A prior award exists”. No paragraph asserts the doctrinal predicate its gate approximates. BANNED_ASSERTIONS in tests/test_doctrine_content.py holds that line: it fails the build if any hook’s prose starts asserting a fact the seed cannot establish.

Supported is not the same as rendered

A hook passing its prerequisite guarantees the argument is coherent; it does not guarantee the case emits a document that hook targets. Five of the rating doctrines — ogilvie, almaraz_guzman, benson, kite, sibtf — land most of their language on trial and petition paper, so a case that stops at pre_trial can carry them without a single contentFlags entry. Two ways to close that gap, both live-verified:

  • Let the lifecycle reach the paper. Add resolution: {type: findings_award} and a target_stage of resolved or later; the trial brief that appears is a target of all five. This is what the fragments in Section 9 do.
  • Force a target subtype. documents.overrides: [{subtype: TRIAL_BRIEF, count: 1}] plants one regardless of stage — but forcing a subtype the lifecycle would not have proposed is itself a WARN (see Document controls), so prefer the first route when you can.

Determinism properties

  • The content table is a frozen dataclass of literal strings — no drawing, no formatting from case facts, so injection consumes no randomness and cannot perturb any other draw.
  • Sections are emitted in table order, not seed order.
  • Injection happens at render time by subclassing the substrate’s own template class and extending its story, so a flagged document uses the same template as an unflagged one and validate --out still reports zero fallbacks.
Hook count changes the whole case, and that is not the injection Naming two or more hooks flips the derived case complexity to complex, which changes document counts and content across the entire case — not just the flagged documents. So a two-hook case and a one-hook case are not a controlled comparison, and diffing them will show far more than the injected sections. To isolate the injection itself, hold the hook count fixed. This coupling predates content injection and is pinned by a test so it cannot change silently.

zeroRealPii is computed, not asserted

The flag is derived from the case’s own castProvenance map, which records where every name came from — seed, faker, engine, or seed_denylisted. Only the first three are in the synthetic-provenance set. If a seed names an entity that hits the shipped real-entity denylist, the engine keeps the name (an explicit seed wins), warns, records that field’s provenance as seed_denylisted, and zeroRealPii computes to false for that case. It is a measurement of the cast, not a constant the generator writes.

The denylist is not only the shipped list of real entities: name_denylist.py also reads the substrate’s four organization pools live, so real employers, carriers, defence firms and medical facilities that exist upstream cannot go stale here. Where a seed does not name its own, the engine substitutes coined organizations rather than drawing from those pools at all.

Provenance and substrateSha

Every document’s content ultimately comes from the substrate’s templates and content pools, so “same seed, same version” is only half the provenance story — a manifest that doesn’t name the substrate can’t be reproduced from itself. provenance.substrateSha records the last commit that touched packages/merus-test-data-generator specifically (not the monorepo HEAD, which moves on every unrelated commit), or unknown outside a git checkout. substrate_pin.txt in the package root records the commit the determinism gates were last verified against; generating against anything else logs a WARN and never fails — moving to a newer substrate deliberately is normal, and only the operator can tell deliberate from accidental.

Synthetic-data markers

Every emitted file says what it is. Live-verified: .eml files carry an X-Synthetic-Data: true header. All markers are applied before the manifest checksum is taken, so a marker can never invalidate a recorded MD5. These are metadata-only markers — see Known limitations for why a visible page watermark isn’t possible from this package.

Determinism guarantees

Same seed plus same engine version produces the same bytes — on any machine, in any timezone, on any day — including every MD5 in the manifest. Manifests carry no generation timestamp, precisely so this guarantee stays independently verifiable.

Verify it yourself

Same-machine determinism was real; cross-machine determinism was not, and the tree would equally have drifted from one calendar day to the next. Scan simulation is seeded explicitly from sha256(rng_seed, "scan:<index>") rather than the substrate’s hash()-derived seed, for the same reason.

Library-mode caveat

The PYTHONHASHSEED=0 pin is applied by re-executing the process, and only the CLI entry point does that (wc-caseload … or python -m wc_caseload_engine …). Importing this package as a library skips it entirely.

If you consume wc_caseload_engine as a library rather than through the CLI, you must either:

  • call wc_caseload_engine.determinism.ensure_stable_hashing() before generating anything, or
  • start the interpreter with PYTHONHASHSEED=0 already set.

Without one of those, output stays self-consistent within a single process but will differ between processes. WC_CASELOAD_NO_REEXEC=1 suppresses the re-exec (useful under a debugger) with the same consequence — use it only when you understand you’re trading away cross-process determinism.

Section 13

Troubleshooting

Substrate bridge errors

The substrate (packages/merus-test-data-generator) is consumed as a library via a documented sys.path bridge in substrate.py — the only place in this package that touches sys.path. Its own modules import each other as top-level packages (data.x, pdf_templates.y), so the substrate root must be discoverable.

  • If the substrate can’t be located, set WC_CASELOAD_SUBSTRATE=/abs/path/to/merus-test-data-generator to point at it explicitly.
  • The bridge path is appended to sys.path, not prepended, specifically so it can never shadow this package’s own modules or a same-named test module. If you see an import resolving to the wrong package, check for a naming collision rather than assuming the bridge is broken.
  • If an import from the substrate breaks after a substrate change, the fix belongs in the bridge (substrate.py / lifecycle_bridge.py) — never by copying substrate files into this package. No module from merus-test-data-generator is ever duplicated here; that invariant is itself tested.

Runway rejections

See Section 3 for the full mechanics and exact error text. In short: if generate or validate exits nonzero naming injury.date_of_injury and a runway shortfall in days, either move the date of injury earlier by the stated amount, or reduce lifecycle.target_stage/drop reconsideration.enabled/liens.post_resolution_litigation to a driver with a smaller floor. Auto-derived (auto:) seeds cannot hit this error by construction; only hand-written seeds can.

Taxonomy drift

Run wc-caseload taxonomy-check to compare the engine’s taxonomy against the classifier source tree at runtime. A clean run looks like this (live-verified):

classifier source : ~/projects/Adjudica-classifier
classifier subtypes: 353
engine subtypes    : 353
drift: none — engine taxonomy matches the classifier exactly

If it exits nonzero, the classifier’s subtype set has moved out from under the engine’s pinned taxonomy. Point --classifier-path (or WC_CASELOAD_CLASSIFIER) at the correct checkout if the default (~/projects) isn’t where it lives, and if the diff is real, the engine’s taxonomy module needs to be updated to match — do not hand-edit a manifest to paper over drift, since validate --out checks every manifest subtype against the same taxonomy.

Other quick checks

  • Nothing renders / command hangs: generation never touches the network by design, so a hang is not a connectivity issue — check the substrate bridge first.
  • Suspiciously few documents for a seeded case: check documents.global_cap and any exclude/include_only entries before assuming the lifecycle is broken; the precedence order in Section 6 usually explains a shorter-than-expected plan.
  • Output looks different than last time for the same seed: confirm you generated through the wc-caseload CLI (or python -m wc_caseload_engine) rather than importing the package as a library without pinning PYTHONHASHSEED — see the library-mode caveat in Section 11.
Section 14

Known limitations

These are documented, deliberate trade-offs rather than bugs — each one was weighed against patching the substrate in place, and left as a surfaced limitation because patching would have introduced shared mutable state or forfeited the substrate’s reuse value.

Hardcoded applicant-firm letterhead

The substrate’s data/docx_styles.py renders Martinez & Associates, APC on the letterhead of every document, regardless of what you set in profile.attorneys.applicant_firm. That field is faithfully recorded in the seed and in the manifest’s applicantFirm field — live-verified across multiple demo cases, including one where defense_firm was explicitly overridden and applicant_firm was not — but it does not change the rendered letterhead text. Patching the substrate’s private constant at runtime would create shared mutable state across cases running in the same process, so this is left as a documented limitation rather than worked around.

Synthetic-data markers are metadata-only

Every file is marked as synthetic in its metadata — /Subject and /Producer for PDFs, core_properties.comments for .docx, an X-Synthetic-Data: true header for .eml (the last confirmed live). None of this is a visible watermark on the rendered page itself — that would have to come from the substrate’s page templates, which this package does not edit.

Doctrine prose is fixed text, and a gate is an approximation

All 14 hooks now inject doctrine-specific language into the documents they target (Section 8), verified end to end: every marker is findable in a rendered PDF of examples/doctrine-showcase.yaml. Two honest limits remain on what that language is.

First, each hook’s paragraphs are literal, fixed text — chosen for the doctrine, not composed from the case. That is what makes injection free of randomness and byte-stable, but it also means the prose never names this applicant’s body parts, this QME’s findings or this employer’s conduct. The surrounding document supplies the facts; the doctrine section supplies the argument.

Second, some prerequisites approximate a legal predicate the seed schema cannot express — either a discrete entity it has no field for (a second injury, a prior award, a prior disability, a diagnosis) or the grounds of the dispute itself (a commute defence, a misclassification defence, a personnel action). The README’s exact/approximation table settles which hooks these are. Rather than let a gate imply more than it checks, those hooks’ paragraphs are written as a contention register: what each side asserts, what the trier must decide. No paragraph asserts the doctrinal predicate its gate approximates, and a test enforces that. If you need prose that finds those facts rather than framing them as contested, that needs richer seed fields first, not richer prose.

Lien and reconsideration documents are template variants, not bespoke templates

The lien and recon machines produce real, correctly-formatted documents, but several of them render through a shared underlying template distinguished only by a variant string: LIEN_RESOLUTION and LIEN_STIPULATION_AGREEMENT both render through the Stipulations template; PETITION_RECONSIDERATION_FILED renders through ApplicationForAdjudication; ORDER_ON_RECONSIDERATION and AMENDED_FINDINGS_AWARD both render through MinutesOrders. The documents are correct-looking and subtype-accurate, but if you need the two lien resolution flavors (or the recon documents) to look structurally distinct at the template level rather than just differ by heading and content, that is a substrate-level template gap, not a configuration you can change from a seed.

Vocabulary is not coverage

Not strictly a defect, but worth restating here: the engine can name 353 canonical subtypes, but a given caseload only emits whatever its seeds’ lifecycles call for — the seven-case demo lands at 83 distinct subtypes, 23.5% of the taxonomy (see subtypeCoverage in Section 10). Raising coverage for a classifier corpus means writing seeds and document-control overrides that deliberately reach the untouched subtypes; it does not happen by generating more cases from the same distributions.

The substrate’s 384-key enum vs. the classifier’s 353 canonical subtypes

The substrate enum carries 384 keys: 350 canonical plus 34 local realism subtypes (fax cover sheets, blank scanned pages, internal file notes) that are not classifier vocabulary. Those 34 are never written to a manifest — 11 map to an unambiguous canonical equivalent and the rest are dropped outright, deliberately conservatively, because a wrong mapping would silently poison the accuracy corpus this engine exists to feed.
